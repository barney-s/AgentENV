## Attempt Log

### Attempt 1 (Failure at VM Creation)
- **What Failed:** The VM creation command failed immediately because the image family name specified in the initial `params.env` (`ubuntu-2404-lts`) was not recognized by Google Compute Engine in the `ubuntu-os-cloud` project.
- **Evidence:** 
  ```
  ERROR: (gcloud.compute.instances.create) Could not fetch resource:
   - The resource 'projects/ubuntu-os-cloud/zones/us-central1-a/imageFamilyViews/ubuntu-2404-lts' was not found
  ```
- **Changes Applied:** 
  1. Updated `IMAGE_FAMILY` to `ubuntu-2404-lts-amd64` in `docs-exploration/runbook-deployments/vm1/params.env`.
  2. Updated the documentation in `docs-exploration/runbooks/deploy-gcevm.md`.
  3. Added a comment note documenting the change at the top of `docs-exploration/runbook-deployments/vm1/deploy.sh`.

### Attempt 2 (Failure due to Polling Race Condition)
- **What Failed:** The GCE VM was successfully created, but `deploy.sh` exited early because of a race condition in the polling logic. It used a simple `systemctl is-active google-startup-scripts.service` check. On fresh boot, there is a short delay before systemd initializes and starts this service, meaning the service was briefly `inactive (dead)` initially. This caused the loop to exit immediately under the assumption that installation was complete, proceeding to compile AgentENV before tools like `make` were actually installed.
- **Evidence:**
  ```
  /root/vm_setup.sh: line 34: make: command not found
  ```
- **Changes Applied:**
  1. Added a robust sentinel file writing step (`echo 'done' > /var/run/startup-script-finished`) at the end of the VM's startup script.
  2. Redesigned the polling loop in `deploy.sh` to wait until `/var/run/startup-script-finished` exists before proceeding.
  3. Cleaned up the broken VM via `teardown.sh` before retrying.

### Attempt 3 & Hardening (Out of Disk Space & IPv4 Forwarding Issues)
- **What Failed:** 
  - **No Space Left on Device:** The default GCE boot disk size is 10GB. Compiling the full AgentENV Rust workspace and its massive native C++ dependencies (such as RocksDB inside `librocksdb-sys`) consumed 100% of the disk, causing cargo build to fail.
  - **IPv4 Forwarding Disabled:** Once the build completed, the server failed to start because IPv4 forwarding was disabled in the guest kernel by default.
- **Evidence:**
  - *Disk Space:* `No space left on device (os error 28)`
  - *Network:* `Error: host IPv4 forwarding is disabled; run 'server --setup-host' as root`
- **Changes Applied:**
  1. **Disk Resizing:** Resized the persistent disk to **50GB** online in GCP, ran `growpart` and `resize2fs` inside the VM, and updated `deploy.sh` and `deploy-gcevm.md` to request `--boot-disk-size=50GB` by default.
  2. **IPv4 Forwarding:** Enabled IPv4 forwarding in the VM kernel (`sudo sysctl -w net.ipv4.ip_forward=1`) and persisted it in `/etc/sysctl.d/99-aenv.conf`.
  3. **Re-compilation & Restart:** Successfully re-compiled and restarted the server.
